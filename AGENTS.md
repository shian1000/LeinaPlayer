# AGENTS.md

## Project

MusicDatabaseApp is the mobile frontend for [MusicDatabase](../MusicDatabase) — a personal music
library / metadata enrichment tool. MusicDatabase today is a Python terminal app with a local
SQLite database and enrichment from MusicBrainz, Wikipedia, iTunes, and Genius.

This app is a Flutter client, targeting Android first, with iOS support kept buildable for a
possible future release. It does not implement any business logic itself — that lives in
MusicDatabase. This app is a presentation/consumption layer only (see
[`docs/decisions/0001-project-setup.md`](docs/decisions/0001-project-setup.md)).

Current state: bootstrap only. `lib/main.dart` renders a static "Hello World" screen. There is no
networking, no state management, and no connection to MusicDatabase's data yet.

## Sources of truth

- Business logic, data model, and enrichment rules live in `MusicDatabase`, not here. Do not
  duplicate them in this repo.
- How the two projects will actually communicate (REST API? local file access? something else?)
  is not decided yet. Do not assume a transport and wire it up silently — check with the user
  first, and record the decision as an ADR in `docs/decisions/`.

## Standard commands

```bash
flutter pub get              # install dependencies
flutter run                  # run on a connected device/emulator
flutter analyze              # static analysis — run before considering a change done
flutter test                 # run widget/unit tests
flutter build apk            # build a release Android APK
```

## Project layout

- `lib/main.dart` — app entry point.
- `lib/src/` — application code, created as the app grows (not present yet at bootstrap).
- `test/` — widget/unit tests, mirrors `lib/`.
- `android/`, `ios/` — platform projects generated by `flutter create`. Avoid hand-editing
  generated platform files unless a specific platform integration requires it.
- `docs/` — documentation for humans and AI agents (see [`docs/index.md`](docs/index.md)).

## Coding conventions

- Follow standard Dart/Flutter style; keep `flutter analyze` clean (the default
  `analysis_options.yaml` from `flutter create` is the baseline — do not weaken its rules without
  discussion).
- Prefer `StatelessWidget`/`StatefulWidget` composition over premature abstraction. Do not
  introduce a state-management package (Provider, Riverpod, Bloc, etc.) or a networking layer
  until there is an actual feature that needs it.
- No comments explaining *what* code does; only *why*, when non-obvious.

## Testing & verification

- Run `flutter analyze` and `flutter test` before considering a change complete.
- For UI changes, actually run the app (`flutter run` on the Pixel 7a emulator or a connected
  device) and look at it — a green test suite does not confirm the screen looks right.

## Git policy

- This is a separate git repository from `MusicDatabase`; do not assume shared history or try to
  reference `MusicDatabase` commits from here.
- Only commit when explicitly asked. Do not push to any remote — the user pushes via their own
  IDE (VS Code or Android Studio).
